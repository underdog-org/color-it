## 0. 本文件的前提

**所有週數都建立在以下配置上。配置改變，整份時程作廢。**

| 項目 | 假設 |
|---|---|
| 工程 | **1 人全職** |
| 繪師 | 外包，1 位，穩態產能每週 3–5 張 |
| v1 平台 | **iOS only**。Android 移出 v1，見 §5 |
| 上架形式 | 先 soft launch（單一市場），再正式上架 |

**這個配置的直接後果**：工程是關鍵路徑（約 38 週），繪師不是（量產只需 15 週）。這與 v0.1 的假設完全相反，v0.1 的「三軌並行」在單人配置下不成立。

## 1. 執行策略

### 1.1 一條主軌 ＋ 一條外部軌

單人開發沒有並行可言。真正能並行的只有**外包繪師**這條外部軌。

```
        W0   W4   W8  W12  W16  W20  W24  W28  W32  W36  W38
        ├────┼────┼────┼────┼────┼────┼────┼────┼────┼────┤

工程軌  ██M0██ █S0█ ██████E1██████ ████E2████ █████S1█████
        資產管線 契約   手感切片      工具集     Gallery/Canvas
                                    
                        █████E3█████ ███S2███ ██SL██ ████S3████ ███R1███
                        Undo/OpLog   Share/IAP soft   雲端/備份  正式上架
                                               launch

繪師軌  ███ 規格對齊 ＋ 3 張試作 ███
        ▲D1                        ░░ 低速 1張/週 ░░ ███ 量產 3–5張/週 ███
                                                    ▲ 從 W16 起（E1 完成後）
```

### 1.2 為什麼繪師量產要延到 W16

v0.1 假設繪師是關鍵路徑，所以要求 W0 全速啟動。**單人配置下這是錯的，而且有害。**

| 理由 | 說明 |
|---|---|
| **時程上不需要** | 50 張 ÷ 3.5 張/週 = 15 週。R1 在 W35，W16 啟動綽綽有餘 |
| **W16 才第一次看得到真實成品** | E1（W10）完成後，才能看到線稿在真實渲染下的樣子——膨脹 2px、線稿 Multiply 蓋頂、shade 疊加後的實際觀感。在那之前量產 = 賭規格是對的 |
| **現金流** | 單人專案的繪師費是主要現金支出。延後 16 週且能先驗證品質，風險與現金雙贏 |

**但 W0–3 的規格對齊與 3 張試作不能延後**——那是 D1，是整個資產策略的驗證，而且它同時是 E1 的輸入。

W4–15 保持每週 1 張的低速，目的是維持繪師的手感與回饋循環，不是產能。

### 1.3 S0 的理由變了

v0.1 說 `MockEngine` 是「解鎖三軌並行的唯一機制」。單人配置下沒有並行，這個理由消失了。**但 S0 仍然要做，理由換成三條**：

1. **介面紀律**——先定介面，引擎只做被需要的東西，不會過度打磨
2. **卡關時可切軌**——E1 是最高風險的里程碑，卡住時可以轉去做 Shell，而不是空轉
3. **Shell 可獨立除錯**——UI 出問題時能用 Mock 排除引擎因素

`MockEngine` 約 150 行，成本一天，這三條理由任一條都值回票價。

**uniffi 從 S0 就導入**（v0.1 排在 E4）。理由：uniffi 不阻止你改邊界，它讓改邊界**更便宜**（改 UDL 重新生成 vs 手改兩端 binding）。手寫 C ABI binding 再於 E4 全部丟掉，對單人是不可接受的浪費。

## 2. 里程碑

### M0｜資產管線（W0–3）

**最先啟動。** 它同時解除外部依賴（繪師）與 E1 的輸入依賴。

| | |
|---|---|
| **範圍** | baker CLI v1、繪師交付規格、降採樣管線、三張真實線稿跑通全流程 |
| **前置依賴** | 無 |

**產出物**

- `tools/baker` CLI：flats → connected components → region ID → **降採樣** → 膨脹 → `.colorpack`
- **三種降採樣濾波器**（flats 用 majority、lineart/shade 用 box）——見 `architecture.md §9.2`
- `contracts/colorpack.schema.json`
- **繪師交付規格文件**（含解析度、比例、三個檔案的硬性要求，附 CSP 操作說明）
- baker 驗證報告格式（區域數、碎片區域、未指派像素、對齊誤差）
- 三張已烘焙的 `.colorpack`（刻意選：一張簡單、一張複雜、一張細碎區域多的）

**驗收標準**

- [ ] 三張圖皆能產出 `.colorpack`，無未指派像素
- [ ] 區域數與繪師預期一致（人工核對）
- [ ] 刻意放入有縫隙的 flats，baker 必須**拒收**並指出座標
- [ ] **降採樣後（2048 / 1920 輸出解析度）重跑全部驗證仍通過**——碎片區域檢查必須在輸出解析度判定
- [ ] 1:1 與 4:5 兩種比例各跑通一張
- [ ] 繪師依規格獨立完成一張交付，**無需來回澄清**

> 最後一條是真正的驗收：規格文件寫得夠不夠清楚，只有繪師能回答。

### E1｜手感垂直切片（W5–10）★ 最高風險

**只做一支軟圓筆 ＋ 油漆桶。不做抽象、不做 UI 打磨。**

| | |
|---|---|
| **範圍** | Rust ＋ wgpu 起手、composite、`T_wet`、三個 pass、油漆桶 ＋ 擴散動畫 |
| **前置依賴** | M0 產出至少一個 `.colorpack`、S0 |

**產出物**

- iOS 端 `MTKView` ＋ `CADisplayLink` ＋ `InputAdapter`

- One-Euro filter ＋ Catmull-Rom 插值
- **Mask Mode A / B 兩種都實作，可即時切換比較**
- **`docs/perf-baseline.md` 第一版**

**驗收標準**

- [ ] 建立 motion-to-photon 的**量測方法**（高速攝影流程文件化）並取得第一份基準線數據
- [ ] 記錄 frame time p99 與**記憶體峰值**基準線（iOS 高階與中階各一台）
- [ ] 記憶體峰值與 `architecture.md §4.1` 的預算表核對，**若超出則此時調整畫布解析度**（此時繪師尚未量產，代價最低）
- [ ] **主觀手感盲測通過**：三人以上分別試用，皆認為「跟手」。**必須用手指測，不得只用觸控筆**
- [ ] Mask Mode A / B 在真機上完成比較，產品決策拍板
- [ ] 油漆桶擴散動畫時長完成實機調校
- [ ] One-Euro filter 與 `majorRadius` 正規化參數完成實機調校

> **E1 過不了，後面全部沒有意義。** 若手感不達標，先懷疑 present 路徑，觸發 `architecture.md §14 R1` 的退路評估。

**時間盒：8 週。** 超過 8 週仍未通過 D3，停止往下做，重新評估技術路線——單人專案沒有「再多投入一個人」的選項，只有「換路線」或「降目標」。

**內含 D2 spike（1 天，見 §4）**

## 3. 關鍵路徑與外部前置

### ★ 關鍵路徑是工程，不是繪師

**這與 v0.1 的結論相反，原因是配置從「多人三軌」變成「1 人」。**

| 路徑 | 長度 |
|---|---|
| **工程（序列）** | **約 38 週** ★ 關鍵路徑 |
| 繪師量產（50 張 ÷ 3.5 張/週） | 15 週，W16 啟動即可在 W31 完成 |

**因此**：

1. **加快上架的唯一手段是砍工程範圍**，增加繪師投入沒有任何幫助
2. 繪師的規格對齊（W0–3）仍是硬前置，但量產可以延後——見 §1.2
3. 若要壓縮時程，優先砍的順序是：S3 的手動匯出/匯入 → 縮時影片的進階選項 → 圖庫數量。**不砍縮時影片本身**（它是唯一的自然傳播來源）

### 外部前置

| 前置 | Lead time | 必須何時啟動 | 若延誤的後果 |

## 4. 決策點

在這些節點量測，若不達標則走既定退路。**退路要事先寫下來，不要在當下臨時想。**

| # | 時點 | 量測什麼 | 不達標時 |
|---|---|---|---|
| **D1** | M0 結束（W3） | 繪師能否穩定依規格交付 flats | **最重的一個技術決策點。** 若不可行，整個資產策略需重新評估（自動區域切割的難度高一個量級）。**不要繼續往下做工程** |
| **D2** | E1 期間（W6，1 天 spike） | 低階 Android 對 wgpu ＋ R16Uint ＋ NEAREST 的支援 | ID map 降級為 RG8 打包。**即使 v1 不做 Android 也必須驗證**——它保護的是資產格式，拖到 Android 版才發現要重烘全部圖庫 |
| **D3** | E1 結束（W10，時間盒 W12） | motion-to-photon 基準線 ＋ **手指**主觀手感盲測 | 檢查 present 路徑；必要時觸發 `architecture.md §14 R1`（改手寫 Metal，影響限於 `render` crate）。超過時間盒則停止並重新評估技術路線 |
| **D4** | E1 結束（W10） | Mask Mode A / B 的實機比較 ＋ 記憶體峰值 | Mask 決策寫回 `prd.md §4.1`；記憶體超標則**此時調整畫布解析度**（繪師尚未量產，代價最低） |
| **D5** | E2 結束（W14） | 五支筆刷差異是否一眼可辨（**手指、已鋪底畫布**） | 砍掉或重調無法辨識的 preset。**寧可四支好用，不要五支有一支多餘**（PRD P2）。水彩是風險最高的一支，見 `architecture.md §14 R7` |
| **D6** | S2 中（W25） | 沙盒 IAP 是否走通 | 若受阻於帳務審核，立即升級為對外溝通事項，不要當工程問題處理 |
| **D7** | SL 觀察期結束（W33） | **soft launch 的付費轉換率** | ★ **最重要的商業決策點。** 若轉換遠低於預期，問題在獲客或定位，不在圖庫數量——此時應調整定位與商店素材，而不是繼續補圖。必要時延後 R1 |
| **D8** | R1 前（W34） | 圖庫是否達 50 張 | **砍數量，不砍功能。** 40 張功能完整優於 50 張功能殘缺 |

## 5. 單人專案的特有風險

| 風險 | 說明 | 處理 |
|---|---|---|
| **卡關無人可換手** | E1 的 wgpu / Metal 問題可能卡住數天而無人可問 | E1 設 8 週時間盒；卡住時切去做 S1（Mock 已就緒），不要空轉 |
| **範圍蠕變** | 沒有他人把關，容易在引擎上過度打磨 | S0 的介面就是範圍契約——介面沒有的能力不做 |
| **Bus factor = 1** | 所有決策脈絡都在一個人腦中 | 這三份文件就是解方，**決策改變時必須即時寫回文件**，不要等有空 |
| **驗收標準自己給自己打分** | 盲測、手感這類主觀項目無法自評 | D3 / D5 的盲測**必須找外部受試者**，不得自評 |

## 6. v1 之後

**以下皆未承諾，僅記錄已知方向，避免在 v1 期間被討論打斷。**

排序依據是「對留存與續訂的預期影響」，實際優先序需上線後依真實數據重排。

### 第一優先｜Android（原 E4 ＋ I2）

移出 v1 的理由：單人配置下，Compose 版四條路由 ＋ Play Billing ＋ Auto Backup 至少 4–6 週，而 v1 的核心假設（有沒有人付錢）在 iOS 上就能驗證。

**v1 已經為它付的預付款**：

- Rust 核心跨平台，`render` crate 用 wgpu 而非 Metal
- uniffi 從 S0 就導入，Kotlin binding 是加一行設定
- D2 已驗證資產格式在 Android 可用
- `architecture.md` 的 Android 欄位全部保留為規格

**還要做的**：Android `engine-bridge`、Compose Shell、Play Billing、Auto Backup（含 25MB 配額策略）、三檔裝置的效能基準線與最低支援規格。

### 其餘方向

| 方向 | 說明 | 預估依賴 |
|---|---|---|
| 縮時影片優化 | 若 v1 數據顯示分享率高，值得投入更多（濾鏡、配樂、比例選擇） | 無 |
| 主題色盤 | 節慶、莫蘭迪等預設調色盤。低成本、高感知價值 | 無 |
| 陰影層開關 | 讓使用者決定要不要 `T_shade` | 資產需標記 shade 是否可選 |
| iPad 專屬佈局 | 平板使用者的體驗目前是放大的手機版 | 無 |
| Apple Pencil 進階 | 雙擊切換工具、懸停預覽 | InputAdapter 擴充 |
| 更多筆刷 | **需要證據支持**——若數據顯示使用者只用兩支，加筆刷是反向操作 | 需 v1 使用數據 |
| Widget | 顯示進行中的作品 | 無 |
| 更多語言（德、西） | i18n 結構已在 v1 建立，加語言是內容工作 | 無 |

### 明確不在 v1 之後的規劃中

`prd.md §9 Don't Have` 列出的項目（社群、帳號、跨平台同步、廣告、遊戲化、AI 上色、匯入自訂線稿）**不因 v1 上線而重新開放討論**。若要推翻，需要先推翻 `prd.md §3` 的核心原則。
