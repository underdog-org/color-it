**產出物**

- **iCloud Drive ubiquity container 備份與還原**（已拍板，見 `architecture.md §11.3`）
- 設定頁的「備份」區塊（Settings 是 **v1 的第五條正式路由**）
- `asset_hash` 失效時的唯讀降級處理（PRD P1-b）

**實作清單**

*iCloud Drive 備份*

- [ ] iCloud container 設定 ＋ ubiquity container 目錄結構（**文件放子資料夾**以降低誤刪風險）——**container 本身需在 W31 前設定完成**
- [ ] **`NSFileCoordinator` 包住所有讀寫**，與 `architecture.md §8.3` 的 atomic rename 一起設計
- [ ] **`NSMetadataQuery` 監聽下載狀態 ＋ `startDownloadingUbiquitousItem`**——換機還原時檔案是 placeholder，不能假設 `FileManager` 讀得到內容
- [ ] **`NSFileVersion` 衝突解析**：保留最後修改者，**衝突版本另存不刪除**（P1）
- [ ] 未登入 iCloud 的降級：設定頁備份區塊顯示「未啟用」並引導至**手動匯出**（S2b 已完成）——**不彈窗、不阻斷**
- [ ] 配額接近上限的降級（E3 已實作策略，此處接上實際配額查詢）

*設定頁與降級*

- [ ] 設定頁的「備份」區塊：說明備份範圍與限制——**Settings 是第五條正式路由**（wireframe 已在 S1），不是憑空長出來的畫面；**不在 onboarding 提**（`prd.md §8`）
- [ ] `asset_hash` 失效時以唯讀模式開啟並顯示縮圖——**絕不刪除文件、絕不套用錯誤資產**

**驗收標準**

- [ ] iOS 換機還原：作品清單與 palette 完整還原
- [ ] 備份總量接近配額上限時的行為符合設計（不得靜默失敗）
- [ ] 刻意提供不存在的 `asset_hash`：作品以唯讀模式開啟，**不被刪除、不套用錯誤資產**
- [ ] 本里程碑期間改變的決策已寫回 `prd.md` / `architecture.md` / `roadmap/`，沒有只存在於腦中的決定

> **為什麼從 4 週縮為 3 週**：S3 原為 W31–34、14 條，資產分發前移到 S1、解鎖 Worker 前移到 S2、手動匯出前移到 S2b 之後只剩 8 條。省下的一週給 S2b，全線仍是 38 週。`architecture.md §11.3` 把 iCloud 的排程風險估為「低—中」，8 條給 3 週是保守的。
