# 決策點與外部前置

> [里程碑索引](./README.md)

**這份是執行時要查的東西**：走到某個時點該量什麼、不達標怎麼辦、哪些行政流程要先啟動。

## 關鍵路徑是工程，不是繪師

**這與 v0.1 的結論相反，原因是配置從「多人三軌」變成「1 人」。**

| 路徑 | 長度 |
|---|---|
| **工程（序列）** | **約 38 週** ★ 關鍵路徑 |
| 繪師量產（低速 9 張 ＋ 量產 41 張 ÷ 3.5 張/週） | 約 12 週，W16–27 完成 |

**因此**：

1. **加快上架的唯一手段是砍工程範圍**，增加繪師投入沒有任何幫助
2. 繪師的規格對齊（W0–1）仍是硬前置，但量產可以延後（W16 啟動即可在 W27 完成）
3. 若要壓縮時程，優先砍的順序是：**縮時影片的進階選項 → 圖庫數量 → i18n 減為英繁兩語，日文延後至 v1.1**。
   - **不砍縮時影片本身**（唯一的自然傳播來源）
   - **繁中不砍**——自己寫、成本近零，且 `prd.md §2` 說它的用途就是驗證 i18n 結構。真正貴的是日文：翻譯外包 ＋ S1 的日文長字串全畫面版面檢查
   - **不砍手動匯出/匯入**——它是 P1 的逃生口，且已前移到 S2b（W28）搶在 SL 上架之前。走系統「檔案」App，不依賴 ubiquity container，成本只有一個分享面板入口，砍它省不到時間

## 決策點

在這些節點量測，若不達標則走既定退路。**退路要事先寫下來，不要在當下臨時想。**

**每個決策點同時是重新校準時程的時機**（38 週是零 buffer 的排法，對外一律講 W40–44）。走到每個 D 時，除了回答「達不達標」，也要回答「後面還剩幾週」。

| # | 時點 | 量測什麼 | 不達標時 |
|---|---|---|---|
| **D1** | **繪師首次獨立交付時（W5–7）** | 繪師能否**在無來回澄清的情況下**依規格交付 flats ＋ reference | **最重的一個技術決策點。** 若不可行，整個資產策略需重新評估（自動區域切割的難度高一個量級）。**不要繼續往下做工程**。時點推算：W1 發出徵才 → 徵到人 W3–5 → 繪製一張含 flats／reference 的完整素材再加 1–2 週。註：M0 / M1 的三張試作由工程自製，驗證不了這一條。**若 D1 未能在 E1 結束（W10）前取得，E2 不啟動，改為延長 E1 的調校時間。** |
| **D2** | E1 期間（W6，1 天 spike） | 低階 Android 對 wgpu ＋ R16Uint ＋ NEAREST 的支援 | ID map 降級為 RG8 打包。**即使 v1 不做 Android 也必須驗證**——它保護的是資產格式，拖到 Android 版才發現要重烘全部圖庫 |
| **D3** | E1 結束（W10，時間盒 W12） | motion-to-photon 基準線 ＋ **手指**主觀手感盲測 | 檢查 present 路徑；必要時觸發 `architecture.md §14 R1`（改手寫 Metal，影響限於 `render` crate）。超過時間盒則停止並重新評估技術路線 |
| **D4** | E1 結束（W10） | Mask Mode A / B 的實機比較 ＋ 記憶體峰值 | Mask 決策寫回 `prd.md §4.1`（**同時結案附錄 A6**）；記憶體超標則**此時調整畫布解析度**（繪師尚未量產，代價最低）。E2 的「Mask Mode 參數化」一條依此結果定案 |
| **D5** | E2 結束（W14） | 五支筆刷差異是否一眼可辨（**手指、已鋪底畫布**） | 砍掉或重調無法辨識的 preset。**寧可四支好用，不要五支有一支多餘**（PRD P2）。水彩是風險最高的一支——實作路徑已定（commit 內 unsharp），退路是 `architecture.md §14 R7` 的三段：放大 blur 半徑 → separable blur → **砍成四支**。E2 內對水彩最多投入 3 天 |
| **D6** | S2 中（W25） | 沙盒 IAP 是否走通 | 若受阻於帳務審核，立即升級為對外溝通事項，不要當工程問題處理 |
| **D7** | SL 觀察期結束（W34） | **soft launch 的付費轉換率** | ★ **最重要的商業決策點。** 決定的是 **R1 的圖庫規模、行銷投入與正式上架時點**，不是「是否繼續投入」——S3 的備份與設定頁是 P1 的落實，無論 D7 結果如何都要做。若轉換遠低於預期，問題在獲客或定位，不在圖庫數量——此時應調整定位與商店素材，而不是繼續補圖。註：SL 的圖庫是免費 6 ＋ 付費 12 共 18 張，免費張數低於正式版的 8–10 張，**轉換率只能當相對訊號，不可直接外推到正式版** |
| **D8** | R1 前（W34，在 D7 之後） | 圖庫是否達 50 張（繪師量產 W16–27 即可達標，D8 前約有 8 週 buffer，故觸發機率低於原估） | **砍數量，不砍功能。** 40 張功能完整優於 50 張功能殘缺 |

## 單人專案的特有風險

本表編號為 **RS**；`architecture.md §14` 的 **R** 是技術退路編號，兩套不同。

| # | 風險 | 說明 | 處理 |
|---|---|---|---|
| **RS1** | **卡關無人可換手** | E1 的 wgpu / Metal 問題可能卡住數天而無人可問 | E1 設 8 週時間盒；卡住時切去做 S1（Mock 已就緒），不要空轉 |
| **RS2** | **範圍蠕變** | 沒有他人把關，容易在引擎上過度打磨 | S0 的介面就是範圍契約——介面沒有的能力不做 |
| **RS3** | **Bus factor = 1** | 所有決策脈絡都在一個人腦中 | 這三份文件就是解方，**決策改變時必須即時寫回文件**，不要等有空。此機制已落實為每個里程碑驗收標準的最後一條「決策回寫」 |
| **RS4** | **驗收標準自己給自己打分** | 盲測、手感這類主觀項目無法自評 | D3 / D5 的盲測**必須找外部受試者**，不得自評 |
| **RS5** | **設計與品牌由工程自己做** | v0.3 決定不外包設計。工程背景的人容易把「乾淨」當成「好看」，而本產品的差異化恰好是視覺品質（`prd.md §1`） | 三個止血點：① **S0 不做任何視覺設計**，wireframe 與 `DesignTokens` 移到 S1（與高保真設計稿同一里程碑）② S2b 的商店截圖**必須是實際完成稿**，若成品不夠好看，那是素材或渲染的問題，設計救不了 ③ D7 若轉換率偏低，**先檢查商店視覺再檢查產品**——這是唯一能便宜驗證設計品質的機會 |
| **RS6** | **文件與實作漂移** | 三份文件是唯一的決策脈絡載體，但實作清單會被頻繁勾選與改動 | 實作清單的定位是「會變的那一層」，產出物與驗收標準是「相對穩定的那一層」。**清單改動不需要回寫，但產出物或驗收標準要改時，必須連同 `prd.md` / `architecture.md` 一起改** |
| **RS7** | **回歸偵測薄弱** | 全線的自動化測試只有三項：`stroke` golden test（E2）、baker negative fixture（M1）、`document` ＋ `oplog` round-trip（E3）。iOS 端與 UI 層完全沒有自動化測試，全靠手動驗收 | 接受此現狀，但 **E3 的持久化正確性必須有自動化測試**（已列入 E3 實作清單）——那是唯一「錯了會讓使用者作品消失」的一層 |
